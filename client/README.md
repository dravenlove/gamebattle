# 战斗测试客户端

**中文** | [English](README.en.md)

`battle_client.py` 用真实的客户端协议（[`proto/battle_client.proto`](../proto/battle_client.proto)）连上战斗服务，有两个用途：打一场战斗并查看战报，或者按固定速率压测，验证这套战斗在你们的负载下是否可行。

服务端是 Erlang 应用里的测试网关（[`erlang/src/gamebattle_gateway.erl`](../erlang/src/gamebattle_gateway.erl)）。它把请求交给一个固定大小的战斗池：同时最多打 N 场，再多的排队，队列也满了就回 `ERROR_CODE_RETRY_LATER`。

## 准备

1. Python 3.9 或更新版本：

   ```bash
   pip install -r requirements.txt
   ```

   第一次运行时，客户端会根据 `.proto` 生成代码到 `generated/`。`.proto` 改了会自动重新生成。

2. 启动带测试网关的战斗服务，两种方式任选：

   ```bash
   # Docker（镜像里同时有 Port 和 NIF）
   docker build -t gamebattle .
   docker run --rm -p 7000:7000 -e ERLANG_COOKIE=test -e GAMEBATTLE_GATEWAY_PORT=7000 gamebattle

   # 本机（先按 README 构建 Port）
   cd erlang && rebar3 compile
   GAMEBATTLE_GATEWAY_PORT=7000 erl -noshell -pa _build/default/lib/gamebattle/ebin \
     -eval 'application:ensure_all_started(gamebattle), timer:sleep(infinity).'
   ```

网关的设置（应用环境变量优先，其次是操作系统环境变量）：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `GAMEBATTLE_GATEWAY_PORT` | 不开启 | 网关监听的 TCP 端口 |
| `GAMEBATTLE_ENGINE` | `erlang` | 用哪个引擎：`erlang`、`nif` 或 `port`（`port` 一次只能打一场）。关卡 2、3 请用 `nif`，快 7–10 倍 |
| `GAMEBATTLE_BATTLE_WORKERS` | 调度器数（通常等于核数） | 同时打几场 |
| `GAMEBATTLE_BATTLE_QUEUE` | 8 × 同时场数 | 最多排队几场，再多就回“繁忙” |

服务端日志每 10 秒打印一次吞吐，例如 `battles: 16.5/s done, 83.5/s rejected as busy, 4 running, 32 queued`。

## 关卡

关卡和阵容都是演示数据，定义在 [`erlang/src/gamebattle_demo.erl`](../erlang/src/gamebattle_demo.erl)。可以照着这个文件加入你们真实的单位和被动配置，再用客户端去测。

| 关卡 | 内容 | 单场规模（4 核机器实测，纯 Erlang / C++） |
|---:|---|---|
| 1 | 普通战斗：你的阵容对 5 名英雄，每人 1 个群攻技能、3 个被动 | 约 1,400 个事件，6 ms / 2 ms |
| 2 | 混合被动压力：7v7，每人 40 个被动，分布在 7 种触发点上，每个每回合最多 3 次，打满 30 回合，没有人会死 | 约 48,000 个事件，约 190 ms / 35 ms |
| 3 | 连锁压力：7v7，每人 20 个受击或命中触发的伤害被动，每个每回合最多 3 次，打满 30 回合，没有人会死 | 约 110,000 个事件，约 450 ms / 40–60 ms |

“没有人会死”用来近似复活让所有人一直在场的最坏情况。阵容从英雄 1–7 里选，格式为 `英雄:位置`，例如 `--lineup 1:1,2:2,3:3`。

## 打一场：`play`

```bash
python battle_client.py play --stage 1
```

```text
战斗 8732（种子 3801341052434245480）
结果：防守方胜，一方全灭，47 回合，先手值 525 : 525
往返 2.9 ms，战报 10,828 字节，200 步，代表 1,333 个事件

单位    阵营    初始HP        最终HP        最大HP        存活
1001    进攻方  3,400         0             3,400         否
...
战斗过程（显示 40 / 200 步，--show 0 显示全部）
     1  第0回合   开场      触发
          效果：先手，触发被动 703@1001，添加 Buff 703@1001，触发被动 703@1002，... 等 21 项  [21 个事件]
     2  第1回合   先手方    2005（防守方）普攻
          → 1001 受到 277（1 击），HP 3,123  [4 个事件]
     3  第1回合   先手方    2004（防守方）技能 504
          → 1001 受到 110（1 击），HP 3,013
          → 1002 受到 80（1 击），HP 3,720
          ...
          效果：触发被动 701@2004 ×2  [12 个事件]
...
共 200 步：单位行动 198，行动之外的触发 2
```

每一步是一个单位的一次行动（或行动之外的一串触发）：用了什么技能，每个受影响的单位受到多少伤害、几击、几次暴击、治疗多少、最后的 HP，以及触发了哪些被动和 Buff（`701@2004 ×2` 表示单位 2004 的被动 701 触发了 2 次）。

| 参数 | 说明 |
|---|---|
| `--stage N` | 关卡，默认 1 |
| `--lineup 1:1,2:2` | 阵容，默认关卡 1 用英雄 1–5，关卡 2、3 用 1–7 |
| `--detail 档位` | 战报详细程度：`summary` 只要结果，`actions` 按行动聚合（默认），`events` 逐事件（关卡 2、3 会有几 MB） |
| `--show N` | 打印前 N 步或前 N 条事件，`0` 表示全部，默认 40（也可以写 `--events`） |
| `--json 文件` | 把整份战报写成 JSON |
| `--host`、`--port` | 服务地址，默认 `127.0.0.1:7000`，写在子命令前面 |

## 压测：`load`

```bash
python battle_client.py load --stage 2 --rate 100 --duration 30
```

客户端按固定速率发起战斗，不等前一场回来，就像大量玩家同时开战：服务端变慢时，发出的请求并不会减少。每秒打印一行进度，结束时给出汇总和结论：

```text
目标 100 场/秒，持续 20 秒，8 个连接，关卡 2，按行动聚合的战报
   秒   发出   完成   繁忙  错误   在途   本秒p50   本秒p99  接收MB/s
   ...
== 结果
发出 2,000 场（100.0 场/秒），完成 375 场（17.1 场/秒），繁忙拒绝 1,625，其他错误 0，超时未回 0
完成的战斗耗时：p50 2087 ms，p90 2284 ms，p99 2406 ms，最大 2418 ms
结论：没扛住 100.0 场/秒，服务端实际处理能力约 17.1 场/秒。...
```

| 参数 | 说明 |
|---|---|
| `--rate N` | 每秒发起几场，默认 100 |
| `--duration N` | 持续几秒，默认 30 |
| `--connections N` | 用几个 TCP 连接，默认 8 |
| `--detail 档位` | 同 `play`，默认 `actions`。`summary` 只测战斗本身，不含战报开销 |
| `--drain N` | 发完后最多再等几秒收回复，默认 60 |

判断方法：

- “繁忙”是服务端队列已满时的拒绝，说明这个速率超过了服务端的处理能力；
- 繁忙为 0、全部完成、p99 在可接受范围内，才算扛住了；
- 逐步调整 `--rate`，找到繁忙刚好为 0 的速率，就是这台机器在这个关卡上的容量；
- 负载远低于容量时偶尔出现几个繁忙，通常是突发：请求在短暂停顿后集中到达，超过了队列长度。队列长度可以按“能接受的排队时间 × 每秒场数”来设置（`GAMEBATTLE_BATTLE_QUEUE`）。

## 实测：4 核机器

战报用 `--detail actions`，客户端和服务端在同一台机器上（客户端也占一部分 CPU）：

| 关卡 | 引擎 | 目标速率 | 实际完成 | 完成的战斗 p99 | 繁忙拒绝 | 战报流量 |
|---:|---|---:|---:|---:|---:|---:|
| 1 | `nif` | 100 场/秒 | 99.8 场/秒 | 6 ms | 0 | 1.0 MB/s |
| 1 | `erlang` | 100 场/秒 | 99.8 场/秒 | 9 ms | 0 | 1.0 MB/s |
| 2 | `nif` | 80 场/秒 | 79.6 场/秒 | 87 ms | 0 | 18 MB/s |
| 2 | `nif` | 100 场/秒 | 97.2 场/秒 | 418 ms | 1% | 22 MB/s |
| 2 | `erlang` | 13 场/秒 | 12.8 场/秒 | 406 ms | 0 | 3 MB/s |
| 3 | `nif` | 55 场/秒 | 54.2 场/秒 | 374 ms | 0 | 6.5 MB/s |
| 3 | `erlang` | 5 场/秒 | 4.9 场/秒 | 707 ms | 0 | 0.6 MB/s |

- 关卡 2：4 核上 NIF 每秒约 97 场，纯 Erlang 约 13 场，是 7.5 倍。关卡 3：至少 55 场对 5 场，约 10 倍。
- 按行动聚合的战报，关卡 2 每场约 240 KB，关卡 3 约 125 KB；逐事件的完整战报分别是 1.5 MB 和 3.8 MB，流量分别降到 1/6 和 1/30。关卡 3 降得更多，是因为对同一批单位的长串连锁伤害会被汇总成几条。
- 超过容量后，排队中的战斗要等前面的打完，完成的那部分 p99 会变高。超出队列的请求会被立刻拒绝，不会无限排队。

## 每秒 100 场需要多少核

按上面实测的吞吐估算，并按 70% 的 CPU 利用率留出余量。战报按行动聚合（`actions`）：

| 关卡 | C++（`nif` 或 `port`） | 纯 Erlang | 战报流量（按行动聚合） | 战报流量（逐事件） |
|---:|---:|---:|---:|---:|
| 1 | 不到 1 核 | 不到 1 核 | 约 1 MB/s | 约 2.3 MB/s |
| 2 | 约 6 核 | 约 44 核 | 约 24 MB/s | 约 150 MB/s |
| 3 | 约 10 核 | 约 80 核 | 约 13 MB/s | 约 390 MB/s |

- 关卡 1 那种普通战斗，两种引擎都完全够用。
- 被动连锁达到关卡 2、3 规模时用 C++，所需核数是纯 Erlang 的 1/7 到 1/8。前提是战报由引擎直接写出（请求带 `report` 选项，网关总是这样用），见 [docs/engine-benchmark.md](../docs/engine-benchmark.md)。
- 发给客户端的战报用按行动聚合的版本。逐事件的战报在关卡 2、3 每秒 100 场时达到 1.2–3 Gbps。
- 如果同一个节点还跑玩法逻辑，给它留一个核：4 核机器用 `+SDcpu 3:3` 启动（少一个 dirty 调度器），或者改用 Port worker。NIF 占满所有核时，其他进程会被延迟 30–50 ms；留出一个核后约 2 ms，代价是吞吐少四分之一左右。

## 注意

- 测试网关只用于验证和压测：关卡、阵容都是演示数据，没有鉴权。不要把它暴露到公网，也不要在正式服开启。
- 压测客户端本身也要占 CPU。客户端和服务端尽量放在不同的机器上；客户端机器的 CPU 打满时，测出的结果会偏低。
- 表中数据来自 4 vCPU 云容器。换到你们的机器上，用同样的命令重测一遍。
