# Lesson 22: Production troubleshooting and fuzzing

[中文](../22-debugging-and-fuzzing.md) | **English**

> Practice code: `practice/term_fuzz.cpp`, `practice/known_issues.cpp`.
>
> Interviewers love asking "what went wrong in production, and how did you track it down". This lesson first covers the troubleshooting techniques for common C++ server problems (each one actually demonstrated), then fuzzing, and finally a complete record of two real problems I found in this project.

## 1. Kinds of production problems

| Symptom | How you'd investigate in Erlang | Tools in C++ |
|---|---|---|
| Process crash | Crash reports, supervision tree logs | **core dump + gdb** |
| Hang, unresponsive | `observer`, `process_info` to see what a process is waiting on | **Attach gdb to the process** and look at every thread's call stack |
| Memory keeps growing | `recon`, `erlang:memory()` | ASan / LeakSanitizer, valgrind, heaptrack |
| Wrong results | Logs, `dbg` tracing | **Replay locally with the same input** (this project's determinism) |
| Got slower | `eprof`, `fprof` | perf, callgrind (lesson 21) |

The biggest difference between C++ and Erlang: when an Erlang process crashes, the VM tells you which function it was in and why; when a C++ process crashes, it often leaves nothing but an exit code. You need to **prepare** the tools and symbol information **in advance**.

## 2. Crashes: core dump + gdb

A simulated bug: an index computed wrongly, accessing a unit out of bounds.

```cpp
std::int64_t apply_damage(BattleState& state, std::size_t target_index, std::int64_t damage) {
    auto& target = state.units[target_index];      // index not checked
    target.hp -= damage;
    return target.hp;
}
```

Measured:

```
$ ./crash bad
Segmentation fault
exit code 139 (139 = 128 + 11, SIGSEGV)
```

**Exit code 139** means the process was killed by signal 11 (SIGSEGV, a segmentation fault). In this project, Erlang's `gamebattle_port` would receive `{Port, {exit_status, 139}}` and the supervisor would restart the Port (lesson 9). At that point it's essential to log the `battle_id`, `seed` and request contents, or you'll never know which battle triggered it.

### Enabling and analyzing core dumps

```bash
ulimit -c unlimited                       # allow core files (the default is usually 0)
cat /proc/sys/kernel/core_pattern         # where core files go and how they're named
./crash bad                               # → Segmentation fault (core dumped)
gdb ./crash core                          # reconstruct the crash from the program + core file
```

The output in gdb (measured):

```
Core was generated by `./crash bad'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  apply_damage (damage=170, target_index=<optimized out>, state=...) at crash.cpp:8
#1  main (argc=<optimized out>) at crash.cpp:15
```

It points straight to `crash.cpp` line 8, `target.hp -= damage;`. Common commands:

| Command | Purpose |
|---|---|
| `bt` | Call stack |
| `frame N` | Switch to frame N |
| `info locals` / `print x` | Inspect local variables |
| `thread apply all bt` | Every thread's call stack (essential for multithreaded programs) |
| `info registers` | Registers |

### `<optimized out>`: the price of a Release build

Note the `target_index=<optimized out>` above. With optimization on, a variable may live only in a register, or be merged or deleted, and gdb can't see its value. This is the most common obstacle when debugging in production. How to cope:
- build production with `-O2 -g` (`RelWithDebInfo`), keeping at least line numbers and call stacks;
- log enough on critical paths (in this project: `battle_id`, `seed` and the request itself);
- for problems reproducible locally, reproduce them locally with an `-O0` build (see section 5).

### Separate debug symbols

An executable built with `-g` is much bigger. The usual practice is to keep the symbols separately and deploy a stripped version:

```bash
g++ -O2 -g crash.cpp -o crash_full                                         # 69208 bytes
objcopy --only-keep-debug crash_full crash_full.debug                      # symbol file: 57832 bytes
objcopy --strip-debug --add-gnu-debuglink=crash_full.debug crash_full crash_release   # deployed version: 17040 bytes
```

Measured: after the production `crash_release` crashes and produces a core file, as long as `crash_full.debug` is in the same directory (or the debug symbol directory), gdb reconstructs the full call stack and line numbers. Every executable has a **Build ID** (visible with `readelf -n crash_release`), which ensures the symbol file and program come from the same build. **Archive the matching symbol files for every release**, or production core files can't be analyzed.

## 3. Hangs: attaching gdb to a running process

Take lesson 17's program where "two threads lock in opposite order", let it hang, and then:

```bash
gdb -p <PID> -batch -ex "thread apply all bt"
```

Measured output (excerpt):

```
Thread 3 (LWP 4508):
#1  __GI___lll_lock_wait (futex=0x7fff4f6c4560, ...)
#3  ___pthread_mutex_lock (mutex=0x7fff4f6c4560)
#5  std::mutex::lock (this=0x7fff4f6c4560)
Thread 2 (LWP 4509):
#1  __GI___lll_lock_wait (futex=0x7fff4f6c4530, ...)
#3  ___pthread_mutex_lock (mutex=0x7fff4f6c4530)
#5  std::mutex::lock (this=0x7fff4f6c4530)
```

Both threads are stuck in `std::mutex::lock`, waiting on **two different locks** (addresses ending in `4560` and `4530`). Looking further up the call stacks shows which lock each already holds. That's the classic scene of a deadlock.

- `gcore <PID>` takes a core file of a running process without killing it, for leisurely analysis later.
- In this project, when the Port hangs, the Erlang side closes it after the timeout (lesson 9). To find out where it was stuck, the timeout handler could run `gcore` on it before closing it.

## 4. Memory problems

| Tool | Speed | Finds | Suited to |
|---|---|---|---|
| AddressSanitizer | 2–3× slower | Out-of-bounds, use-after-free, leaks (via the bundled LeakSanitizer) | Development and testing; used in every lesson so far |
| valgrind memcheck | 20–50× slower | Same, without recompiling | Programs you can't recompile |
| heaptrack / valgrind massif | Slow | Where memory **growth** happens (not necessarily a leak) | Investigating "memory keeps growing" |

On lesson 14's `shared_ptr` reference-cycle example, valgrind measured:

```
112 (56 direct, 56 indirect) bytes in 1 blocks are definitely lost
   by 0x1092F3: main (cycle.cpp:12)
definitely lost: 56 bytes in 1 blocks
indirectly lost: 56 bytes in 1 blocks
```

"definitely lost" is one buff object; "indirectly lost" is the other object, referenced by it through a `shared_ptr` and therefore not freed either.

Note: **memory that keeps growing isn't necessarily a leak**. It could be an unbounded cache, a queue piling up (lesson 19's backpressure), fragmentation, or a `vector` whose `clear()` doesn't release capacity (lesson 16).

## 5. Wrong results: replaying locally using determinism

This is the project's biggest advantage. The same request + the same seed + the same engine version always give a byte-identical result (lesson 17 measured that this holds across threads too). So:

1. Production finds an anomalous battle result → take that battle's **raw request bytes** (ETF) and engine version from the logs;
2. load those bytes locally into the same engine version, built with `-O0 -g`, and the result is guaranteed to match production exactly;
3. set a conditional breakpoint on `EffectSystem::apply_damage` in gdb (say `break apply_damage if target_index == 3`) and step through.

`--dump-request` in `practice/battle_bench.cpp` is an example of saving a request as an ETF file. A production recommendation: **save the request bytes of every battle that returns an error or triggers an alert**.

## 6. Fuzzing

Unit tests check "the inputs I thought of"; fuzzing checks "the inputs I didn't think of": it automatically generates huge amounts of malformed data, feeds it to the program, and watches for crashes or sanitizer reports.

`wire::handle_etf` is the engine's single entry point from the outside: every byte the Port and NIF receive passes through it. It must guarantee: **any input returns only `{ok, _}` or `{error, _}`, never crashes and never triggers undefined behavior**. In NIF mode especially, a crash here takes down the whole Erlang node.

### The test entry point

```cpp
extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    const auto reply = gamebattle::wire::handle_etf({data, size});   // every input must return normally
    const auto decoded = gamebattle::term::decode(reply);            // our own reply must always decode
    return 0;
}
```

This is libFuzzer's standard entry function. Where libFuzzer is available, compile with `clang++ -fsanitize=fuzzer,address,undefined`, and libFuzzer mutates inputs guided by code coverage, much smarter than random mutation.

The clang on this machine lacks the libFuzzer runtime, so `term_fuzz.cpp` brings its own simple mutation driver: starting from a few valid seed inputs (the sample battle request, `ping`, a `load_config` command, a list of mixed types), it randomly combines these mutations:
- flip a bit;
- change a byte to an "interesting value": 0, 0xFF, the various ETF type tags;
- truncate; insert random bytes;
- splice in a piece cut from another seed;
- **change some 4 bytes to an extreme length value**: 0, 1, 0x7FFFFFFF, 0xFFFFFFFF, 1000000.

### Measured results

Built with AddressSanitizer + UBSan, 200,000 iterations:

```
iterations: 200000 in 154 s, no crash
sampled outcomes:
  error:config_load_failed: 65
  error:invalid_request: 3001
  ok: 59
```

200,000 malformed inputs with no crash, memory error or undefined behavior. The vast majority were correctly judged `invalid_request`, and the few requests still valid after mutation returned `ok` normally. This shows `term.cpp`'s defensive style (lesson 9: check the length before every read, limit nesting depth and element counts) works.

**But "didn't crash" doesn't mean "no problems"**: the next section has a problem random fuzzing struggles to find.

## 7. Real problems found during this course

While writing this course's practice code, I found two real problems in the engine (three counting lesson 21's performance problem). `practice/known_issues.cpp` reproduces them and reports whether each has been fixed. The current output:

```
[1] same inline buff on two units
    Engine::simulate (in process): ok
    wire::handle_etf (over ETF)  : error invalid_request: one battle request contains conflicting definitions for a buff id
[2] 501-byte input of nested lists
    reply: error invalid_request: truncated ETF value
    VmPeak grew by 3814 MB

issue 1 (inline buff conflict)        : PRESENT
issue 2 (nested reserve amplification): PRESENT
issue 3 (slow result encoding)        : run encode_bench to compare
```

### Problem 1: a request is rejected when two units carry the same inline buff

**How it was found**: writing lesson 21's benchmark required converting a request built in C++ to ETF to run the full pipeline. The same request worked when calling `Engine::simulate` directly, but was rejected after going through ETF.

**Root cause**:
- When `wire.cpp:310` parses an inline buff, it calls `std::make_shared<BuffSpec>(...)` to create a new object **every time it meets one**. If two units both carry the "Envenom" passive, you get two `BuffSpec`s with identical contents at different addresses.
- The validation at `battle_state.cpp:159-163` records each buff seen as `buff_id → pointer`, and treats the same id mapping to **different pointers** as "conflicting definitions". It uses "different pointers" to stand for "different definitions", and that premise doesn't hold for inline requests.
- When a request is built directly in C++, the two units share the same `shared_ptr`, so it doesn't trigger. For requests sent with config IDs (`skill_ids`), the buffs come from `ConfigStore` and are also the same shared object, so they're unaffected too.

**Impact**: only **inline-format** requests, and only when two units carry a buff with the same id. In the README's example request each buff appears on only one unit, so it wasn't exposed. The recommended production config-ID approach is unaffected. But "three heroes all carrying the same passive" is a perfectly natural thing to write in inline format, and it gets rejected for no apparent reason.

**Fix options** (pick one):
1. Have `parse_request` keep a `buff_id → shared_ptr` table while parsing: when an id appears a second time, **reuse the first object if the contents are identical**, and only report an error if they differ. This needs deep comparison for `BuffSpec`, `BuffReaction` and `Effect` (note that `Effect::buff` is a `shared_ptr`, whose default `operator==` compares only pointers; what needs comparing is what they point to).
2. Change `validate_request`: when the pointers differ, go on to compare contents.

Option 1 is better: after parsing, each buff exists as a single object, saving memory and matching the behavior of the config-ID path.

### Problem 2: a 501-byte input makes the process reserve 3.8 GB of memory

**How it was found**: reading `term.cpp`, I noticed that when decoding a list, `check_count` only checks that the element count is at most 1 million and then immediately calls `list.reserve(count)`, before confirming that the input actually contains that much data.

**Reproduction**: build 100 levels of nested lists, each claiming 1,000,000 elements (each level takes only 5 bytes):

```
501-byte input of nested lists
reply: error invalid_request: truncated ETF value
VmPeak grew by 3814 MB                        ← the nested-map version reaches 7.0 GB
```

Each level `reserve`s 1 million `Value`s (about 40 MB), recursing 100 levels deep. It eventually returns a "truncated" error because there isn't enough data, and all that memory is freed during stack unwinding.

**Why it normally goes unnoticed**: under Linux's default memory overcommit policy, `reserve` only allocates virtual address space; pages never written to take no physical memory, so resident memory (RSS) stays at 4 MB and the process doesn't crash. Random fuzzing didn't find it either, because random mutation is almost never going to assemble a structure like "100 levels of nesting, each with the maximum count", and it doesn't trigger any sanitizer report.

**When it causes trouble**: when the process has an address-space limit (containers and some hardened environments set one). Measured under `ulimit -v 2000000` (2 GB):

```
reply: error / std::bad_alloc
VmPeak: 1998924 kB                ← one request fills the entire address-space limit
```

- The error type becomes `internal_error` instead of `invalid_request` (scrambling lesson 8's classification);
- at that moment, **every other memory allocation in the same process fails**. In Port mode the damage is limited; in NIF mode, if other BEAM VM threads happen to allocate memory at that instant, the whole Erlang node could crash.

**The fix**: every element takes at least 1 byte, so the number reserved should never exceed the remaining byte count:

```cpp
list.reserve(std::min<std::size_t>(count, bytes_.size() - offset_));   // lists, tuples
object.reserve(std::min<std::size_t>(count, (bytes_.size() - offset_) / 2));   // maps: at least 2 bytes per pair
```

After the change, rerun `known_issues` and item 2 should show `fixed`.

**Lessons learned**:
- "length" and "count" fields in external input must be compared against "the data actually remaining" **before allocating memory**, not just against a fixed limit;
- libFuzzer has a `-malloc_limit_mb` flag that reports "a single allocation over N MB" as an error, designed to find exactly this kind of problem;
- beyond fuzzing, **reading code from an attacker's point of view** matters just as much.

### Two smaller hazards (mentioned in earlier lessons)

- `enif_release_binary` in `nif.cpp` is called by hand with no RAII protection (lesson 9); a `unique_ptr` with a custom deleter fixes it (lesson 14).
- The catch blocks in `handle_etf` still allocate memory (lesson 8). In extreme cases (memory exhausted) an exception would be thrown again from inside a catch block, crashing the node in NIF mode.

All of these are **left for you to fix**: fix them, add tests, commit, which is exactly the "verifiable project experience on your résumé" lesson 24 is about.

## 8. Logging and monitoring

Whether a problem can be tracked down depends on what you left behind beforehand:

- **Every battle carries its `battle_id`, `seed` and engine version.** Save the raw request bytes of battles that go wrong.
- **Translate Port exit codes into readable reasons**: 0 is a normal exit, 2–5 are the protocol errors defined in `port_main.cpp` (lesson 9), 134 is `abort` (an uncaught exception, say, lesson 8), 139 is a segmentation fault.
- **Metrics**: battles per second, latency p50/p99, error rate (counted separately for `invalid_request` / `internal_error`), Port restart count. Any `internal_error` should raise an alert.
- **Keep the scene automatically on a crash**: enable core dumps and archive each version's debug symbols.

## Interview questions

**Q1: A production C++ service crashed. How do you investigate?**
First look at the exit code or signal (139 is a segfault, 134 is abort). Enable core dumps and use `gdb program core` to see the crashing thread's call stack, and `thread apply all bt` for every thread. Build production with `-O2 -g` and archive the separated debug symbols (matched by Build ID). When you hit `<optimized out>`, combine the logs and reproduce locally with the same input on an `-O0` build.

**Q2: How do you investigate a hung program?**
Attach with `gdb -p PID` and use `thread apply all bt` to see where each thread is stopped. Several threads stopped in `mutex::lock` waiting on different locks means deadlock. When you can't stop the service, use `gcore` to produce a core file and analyze it afterwards.

**Q3: How do you investigate a memory leak?**
During development, AddressSanitizer / LeakSanitizer; when you can't recompile, valgrind memcheck (measured: it pinpointed the line of a `shared_ptr` reference-cycle leak). When memory keeps growing without a leak, use heaptrack or massif to see what's growing: possibly an unbounded cache, a queue piling up, or fragmentation.

**Q4: What is fuzzing? How did you do it?**
Automatically generating lots of malformed input and checking whether the program crashes or triggers a sanitizer. For the engine's single external entry point, `wire::handle_etf`, I wrote a libFuzzer-compatible test function and a mutation driver, and ran 200,000 iterations under ASan + UBSan without a crash. Separately, code review turned up a problem random fuzzing struggles to trigger: nested containers preallocated by their declared counts before confirming the data exists, so a 501-byte input could grow peak virtual memory by 3.8 GB.

**Q5: Tell me about a bug you found and analyzed.**
(Problem 1 or 2, told in the order "symptom → reproduction → root cause → impact → fix → verification".) For problem 1: the same request worked when calling the engine directly but was rejected after going through ETF; the cause was that parsing created a new object for every inline buff, while the validation code treated "different pointers" as "conflicting definitions"; it only affects inline-format requests where several units carry the same buff; the fix is to dedupe by id while parsing and compare contents; the `known_issues` program serves as the regression test.

**Q6: Why must you ship Release builds with debug symbols?**
A plain Release build has no symbols, so a core file has only addresses and can't be mapped to source; a plain Debug build is tens of times slower and unusable in production. `-O2 -g` with separated symbols gives a small, fast production binary, and when something goes wrong you analyze it with the archived symbol file.
