# Lesson 24: Résumé and project pitch

[中文](../24-resume-and-pitch.md) | **English**

> The last lesson. The first 23 lessons were about "do you understand it"; this one is about "how do you make an interviewer believe you understand it".

## 1. First, be clear: what this course can and can't give you

**What it can give you**:
- A project with depth that holds up under questioning: a deterministic battle engine + three Erlang integration paths + a config pipeline + a thread pool + an epoll server + performance analysis + fuzzing;
- the reasoning behind every design decision, plus dozens of measured numbers you can quote in interviews;
- a body of knowledge and a question bank covering the main topics of C++ game-server interviews (lesson 23).

**What it can't do for you**:
- **Algorithm problems**: practice those separately (lesson 23, part N).
- **The muscle memory of writing code yourself**: understanding code and writing it are two different things, and an interview may ask you to write a thread pool or an LRU cache on the spot.
- **"Ownership" of the project**: this matters most, so it gets its own section.

### On who wrote the project

This engine was originally generated by you together with Codex, and the practice code in the course was written by me. When an interviewer sees the project on your résumé, they will follow up: why was it designed this way? What happens if this is accessed concurrently? What was the hardest problem you hit? If you've only "read" this code, you'll be found out within three follow-up questions.

So two principles:

1. **Put on your résumé only what you can explain in full detail.** The purpose of this course is to let you explain every line of the engine.
2. **Make the project genuinely yours.** Please complete and commit the fixes and extensions listed in the next section **yourself**. Then every problem you talk about is one you located, fixed and verified with your own hands, and it will naturally stand up to questioning in interviews.

Using AI to assist development isn't a problem in itself; many teams work this way now. What matters is whether you understand and control the code. If an interviewer asks, you can say plainly: "The initial version was generated with AI assistance; after that I systematically reviewed all of the code, found and fixed several problems, and did performance analysis and optimization." That's more credible than pretending you wrote it all from scratch, and it shows more engineering ability.

## 3. How to write the résumé

### Project description (2–3 lines)

> **A deterministic C++20 battle engine callable from Erlang**
> The core of a turn-based battle server: a data-driven skill / passive / buff system that guarantees byte-identical results for the same input and random seed (for battle replays and anti-cheat); supports three integration paths: Erlang Port, NIF and TCP; comes with a CSV → binary config compiler supporting hot reloads without downtime.

### Achievement bullets (pick and adapt according to what you've actually done)

The numbers below come from this course's measurements on a 4-core cloud VM. **Before putting them on your résumé, re-measure on your own machine** and use the numbers you get:

- **Performance**: wrote a segmented benchmark covering the full pipeline and found result encoding took about 78% of the time; callgrind analysis showed `std::initializer_list` was deep-copying the event list; after optimization encoding was about 1.9× faster (about 4× with a streaming encoder), raising single-thread throughput from about 900 to about 1700 battles/s, with output verified byte-identical before and after.
- **Concurrency**: implemented a thread pool running battles concurrently, about 3.5× faster on 4 cores, with results byte-identical to single-threaded and no data races under ThreadSanitizer.
- **Networking**: built a TCP battle service on Linux epoll with a Reactor + worker thread pool: length-prefixed framing (compatible with Erlang `gen_tcp`'s `{packet, 4}`), per-connection ordering, backpressure, graceful shutdown via `signalfd`; single-connection latency p50 about 2.1 ms, p99 about 4.2 ms.
- **Quality**: wrote a fuzz test for the ETF protocol entry point that ran 200,000 iterations under ASan + UBSan without a crash; found and fixed, through code review, a memory amplification problem (a 501-byte input growing peak virtual memory by 3.8 GB) and a problem where inline buffs were misjudged as conflicting.
- **Engineering**: set up CI that automatically runs unit tests, sanitizer builds and fuzzing.

### Skills section

Write what the course covers as keywords interviewers can search for: C++17/20 (move semantics, smart pointers, templates and concepts, `std::variant`), STL internals, multithreading (mutexes / condition variables / atomics / memory orders / lock-free queues), Linux network programming (epoll / Reactor), CMake, gdb / core dumps, AddressSanitizer / ThreadSanitizer / valgrind, performance analysis (callgrind / perf), Erlang/OTP (gen_server, supervision trees, Port / NIF).

**Be ready to be questioned on every word you write down.** Lesson 23's question bank is organized with exactly that in mind.

## 4. Three stories you can tell again and again

Answer project deep-dives with the **STAR** structure: Situation, Task, Action, Result. The three stories below cover the three most common kinds of follow-up: "performance", "troubleshooting", and "design and concurrency".

> The "fixed" and "after optimization" in these stories **assume you have already completed the corresponding tasks from section 2's hands-on list yourself**. Until you have, you can only say "found it, analyzed it, proposed a fix", not "fixed it".

### Story 1: the performance analysis that doubled throughput (lesson 21)

- **Situation**: the engine serves requests through an Erlang Port, and I wanted to know how many battles per second a single Port process could handle and where the bottleneck was.
- **Task**: find the bottleneck and optimize it without changing any output.
- **Action**:
  1. Wrote a benchmark that splits the full pipeline into four timed segments, decoding, parsing, simulation and encoding, tested with 3000 battles with different seeds. The result was unexpected: simulation was only 15%, and **encoding the result was 78%**.
  2. Analyzing with valgrind's callgrind showed over 30% of instructions were spent in `vector` copy constructors.
  3. Reading the code found the cause: when nested maps were built with `std::initializer_list`, the elements were `const` and could only be copied, so the entire event list was deep-copied.
  4. Wrote two alternative implementations: one without the copies, and one that builds no intermediate structure and streams bytes directly. **First verified that the output for 1000 battles was byte-identical**, then timed them.
- **Result**: encoding was about 1.9× and 4× faster respectively, and full-pipeline single-thread throughput rose from about 900 to about 1700 battles/s. Weighing maintenance cost, I adopted the smaller change first.

**Likely follow-ups**:
- *Why not optimize simulation from the start?* → Amdahl's law: simulation is only 15%, so even reducing it to zero gives just 1.18×.
- *How do you make sure the optimization didn't break the results?* → Byte-for-byte comparison, with the comparison test kept permanently in the code.
- *Are the measurements trustworthy?* → Release builds, warm-up, multiple runs; I also hit two cases of fake data "deleted by the optimizer", both caught by converting to "how many clock cycles per operation" (lesson 21).
- *Why can `initializer_list` only copy?* → Lesson 13, section 6.

### Story 2: a 501-byte request (lesson 22)

- **Situation**: the engine's single external entry point is ETF decoding. In NIF mode it runs inside the Erlang VM, so any problem there affects the whole node.
- **Task**: confirm that this entry point is safe for any input.
- **Action**:
  1. Wrote a fuzz test and ran 200,000 iterations under ASan + UBSan, with no crashes found.
  2. But I kept reading the decoding code from an attacker's point of view and noticed that when decoding a list, it only checked the element count against an upper limit (1 million) and then preallocated memory for that count, before confirming the input actually had that much data.
  3. Built an input with 100 levels of nesting, each claiming 1 million elements, only 501 bytes long. Measured, the process's peak virtual memory grew by 3.8 GB (7 GB for the map version).
  4. Analyzed the impact: with the default configuration physical memory is unaffected, but in an environment with an address-space limit, measured, the request exhausts the entire limit and returns a misclassified `internal_error`, and in NIF mode it could also make other BEAM threads' memory allocations fail.
  5. The fix: never preallocate more elements than there are remaining bytes (each element takes at least 1 byte).
- **Result**: the regression test program confirmed the fix, and all fuzz tests pass. I also took away a lesson: length fields in external input must be compared against the data actually remaining before allocating memory.

**Likely follow-ups**:
- *Why didn't fuzzing find it?* → Random mutation struggles to assemble such a deep structure, it doesn't trigger sanitizers, and physical memory doesn't grow. libFuzzer's `-malloc_limit_mb` is designed to catch exactly this.
- *What's the difference between virtual and physical memory?* → Lesson 23, question 80.
- *Why is it more dangerous in NIF mode?* → Lessons 8, 9.

### Story 3: determinism and concurrency (lessons 3, 5, 7, 17, 20)

- **Situation**: battle results must be replayable, verifiable by server-side recomputation, and computable concurrently on multiple threads.
- **Task**: guarantee that the same request gets exactly the same result on any platform and any thread.
- **Action**: explain each source of nondeterminism and its countermeasure: floating point → everything in integers and basis points; standard-library random distributions aren't portable → a hand-written SplitMix64; `std::sort` isn't stable → comparators end by comparing a unique ID; hash-table iteration order → never iterate an `unordered_map`; signed overflow is undefined behavior → saturating arithmetic; multithreading → each battle's state is fully isolated, and the shared config is read-only.
- **Result**: a 4-thread pool running 2000 battles concurrently produced results byte-identical to single-threaded, about 3.5× faster, with no ThreadSanitizer warnings. Thanks to determinism, battle reports need to store only the request (8.6 KB) rather than the result (148 KB).

**Likely follow-ups**:
- *Can old battle reports still be replayed after the code changes?* → Not necessarily; any new random roll shifts every later random number, so battle reports must record the engine version (lesson 3).
- *Why do wrong memory orders not show up in tests?* → Lesson 18.
- *Why does going to 4 threads give less than 4×?* → Contention with the main thread, allocator contention; the measured scheduling overhead of empty tasks (lesson 17).

## 5. One-minute and three-minute project introductions

**The one-minute version** (for your self-introduction; again assuming the hands-on list is done):

> I mainly work on Erlang game servers, and recently I've been building a turn-based battle engine in C++20 that Erlang can call through a Port, a NIF or TCP. Its core feature is determinism: the same input and random seed give byte-identical results on any platform and any thread, which enables battle replays and anti-cheat verification. I did performance analysis on the project and nearly doubled single-thread throughput; I also wrote fuzz tests, and found and fixed a problem that let a 501-byte request take up several GB of virtual memory.

**The three-minute version** (for "tell me about your project"): expand along "architecture → one design highlight → one problem and how you solved it → numbers":
1. Architecture: Erlang handles connections and business logic, C++ handles battle computation; the trade-offs of the three integration paths (lessons 9, 19).
2. Pick one design highlight: the buff system's four orthogonal components (data-driven), config hot reloading's "load outside the lock, swap the pointer inside it", or the determinism safeguards.
3. A problem and how you solved it: story 1 or story 2, whichever you tell best.
4. Close with numbers: throughput, latency, concurrency speedup.

Have an **architecture diagram** ready when you tell it (lesson 19 section 4 and lesson 20 section 1 can both be used directly): share your screen in online interviews, draw it on the whiteboard in person.

## 6. What to do when you're asked something you don't know

- **Don't make things up.** C++ interviewers see through it easily, and once they do, everything you said before gets discounted.
- **Say the part you know, and how you'd go about verifying the rest.** For example, asked about the implementation of `std::atomic<std::shared_ptr>`: "I measured that it isn't lock-free in libstdc++, so it presumably uses a lock bit internally, but I haven't read the source for the details."
- **Steer the question back to familiar ground.** Asked about io_uring, which you haven't used: "I used epoll. I understand the idea of io_uring is batched submission and batched completion to cut system calls. I counted system calls in my project with strace and found the main costs were actually in locks and memory allocation, so for my scenario switching to io_uring would probably gain less than optimizing allocation first."
