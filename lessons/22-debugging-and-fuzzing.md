# 第 22 课：线上问题排查与模糊测试

**中文** | [English](en/22-debugging-and-fuzzing.md)

> 实战代码：`practice/term_fuzz.cpp`、`practice/known_issues.cpp`。
>
> 面试官很喜欢问"线上出过什么问题、你怎么查的"。这一课先讲 C++ 服务端常见问题的排查手段（每一种都实际演示过），再讲模糊测试，最后完整记录我在这个项目里发现的两个真实问题。

## 1. 线上问题的分类

| 现象 | Erlang 里你会怎么查 | C++ 里的工具 |
|---|---|---|
| 进程崩溃 | crash report、监督树日志 | **core dump + gdb** |
| 卡死、不响应 | `observer`、`process_info` 看进程在等什么 | **gdb 附加进程**，查看所有线程的调用栈 |
| 内存一直涨 | `recon`、`erlang:memory()` | ASan / LeakSanitizer、valgrind、heaptrack |
| 结果不对 | 日志、`dbg` 跟踪 | **用相同输入在本地重放**（本项目的确定性） |
| 变慢了 | `eprof`、`fprof` | perf、callgrind（第 21 课） |

C++ 和 Erlang 最大的区别：Erlang 进程崩溃时，虚拟机会告诉你它在哪个函数、为什么崩溃；C++ 进程崩溃时，往往只留下一个退出码。你需要**事先准备好**工具和符号信息。

## 2. 崩溃：core dump + gdb

一个模拟的 Bug：下标算错了，访问了越界的单位。

```cpp
std::int64_t apply_damage(BattleState& state, std::size_t target_index, std::int64_t damage) {
    auto& target = state.units[target_index];      // 没检查下标
    target.hp -= damage;
    return target.hp;
}
```

实测：

```
$ ./crash bad
Segmentation fault
退出码 139（139 = 128 + 11，SIGSEGV）
```

**退出码 139** 表示进程被 11 号信号（SIGSEGV，段错误）杀死。放到本项目里，Erlang 的 `gamebattle_port` 会收到 `{Port, {exit_status, 139}}`，监督者重启 Port（第 9 课）。这时候一定要把 `battle_id`、`seed` 和请求内容记进日志，否则你永远不知道是哪场战斗触发的。

### 开启并分析 core dump

```bash
ulimit -c unlimited                       # 允许生成 core 文件（默认通常是 0）
cat /proc/sys/kernel/core_pattern         # core 文件存放的位置和命名规则
./crash bad                               # → Segmentation fault (core dumped)
gdb ./crash core                          # 用程序 + core 文件还原崩溃现场
```

gdb 里的输出（实测）：

```
Core was generated by `./crash bad'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  apply_damage (damage=170, target_index=<optimized out>, state=...) at crash.cpp:8
#1  main (argc=<optimized out>) at crash.cpp:15
```

直接定位到 `crash.cpp` 第 8 行 `target.hp -= damage;`。常用命令：

| 命令 | 作用 |
|---|---|
| `bt` | 调用栈 |
| `frame N` | 切换到第 N 层 |
| `info locals` / `print x` | 看局部变量 |
| `thread apply all bt` | 所有线程的调用栈（多线程程序必用） |
| `info registers` | 寄存器 |

### `<optimized out>`：Release 构建的代价

注意上面的 `target_index=<optimized out>`。开了优化以后，变量可能只存在于寄存器里，或者被合并、被删除，gdb 就看不到它的值了。这是在线上调试时最常遇到的障碍。应对方法：
- 线上用 `-O2 -g`（`RelWithDebInfo`）构建，至少保留行号和调用栈；
- 关键路径上记录足够的日志（本项目中就是 `battle_id`、`seed`、请求本身）；
- 能在本地复现的问题，就在本地用 `-O0` 构建复现（见第 5 节）。

### 分离调试符号

带 `-g` 的可执行文件会大很多。常见做法是把符号单独保存，线上只部署去掉符号的版本：

```bash
g++ -O2 -g crash.cpp -o crash_full                                         # 69208 字节
objcopy --only-keep-debug crash_full crash_full.debug                      # 符号文件：57832 字节
objcopy --strip-debug --add-gnu-debuglink=crash_full.debug crash_full crash_release   # 部署版：17040 字节
```

实测：线上的 `crash_release` 崩溃产生 core 文件后，只要 `crash_full.debug` 在同一目录（或调试符号目录）下，gdb 就能还原出完整的调用栈和行号。每个可执行文件都有一个 **Build ID**（`readelf -n crash_release` 可以看到），用来确保符号文件和程序是同一次构建的产物。**每次发布都要归档对应的符号文件**，否则线上的 core 文件就没法分析了。

## 3. 卡死：gdb 附加到正在运行的进程

用第 17 课那个"两个线程以相反顺序加锁"的程序，让它卡住，然后：

```bash
gdb -p <PID> -batch -ex "thread apply all bt"
```

实测输出（节选）：

```
Thread 3 (LWP 4508):
#1  __GI___lll_lock_wait (futex=0x7fff4f6c4560, ...)
#3  ___pthread_mutex_lock (mutex=0x7fff4f6c4560)
#5  std::mutex::lock (this=0x7fff4f6c4560)
Thread 2 (LWP 4509):
#1  __GI___lll_lock_wait (futex=0x7fff4f6c4530, ...)
#3  ___pthread_mutex_lock (mutex=0x7fff4f6c4530)
#5  std::mutex::lock (this=0x7fff4f6c4530)
```

两个线程都停在 `std::mutex::lock`，等的是**两把不同的锁**（地址分别以 `4560` 和 `4530` 结尾）。再往上看调用栈，就能看到它们各自已经拿着哪把锁。这就是死锁的典型现场。

- `gcore <PID>` 可以给一个正在运行的进程拍一份 core 文件，不需要杀掉它，事后慢慢分析。
- 本项目中，Port 卡住时 Erlang 侧会在超时后关闭 Port（第 9 课）。如果想知道它卡在哪里，可以在超时处理里先对它执行 `gcore` 再关闭。

## 4. 内存问题

| 工具 | 速度 | 能发现 | 适合 |
|---|---|---|---|
| AddressSanitizer | 慢 2~3 倍 | 越界、释放后使用、泄漏（附带的 LeakSanitizer） | 开发和测试，前面每一课都在用 |
| valgrind memcheck | 慢 20~50 倍 | 同上，不需要重新编译 | 没法重新编译的程序 |
| heaptrack / valgrind massif | 慢 | 内存**增长**发生在哪里（不一定是泄漏） | 排查"内存一直涨" |

用第 14 课那个 `shared_ptr` 环形引用的例子，valgrind 实测：

```
112 (56 direct, 56 indirect) bytes in 1 blocks are definitely lost
   by 0x1092F3: main (cycle.cpp:12)
definitely lost: 56 bytes in 1 blocks
indirectly lost: 56 bytes in 1 blocks
```

"definitely lost" 是一个 Buff 对象，"indirectly lost" 是被它通过 `shared_ptr` 引用、因此同样没被释放的另一个对象。

注意：**内存一直增长不一定是泄漏**。可能是缓存没有上限、队列在堆积（第 19 课讲的背压）、内存碎片，或者 `vector` 的 `clear()` 不释放容量（第 16 课）。

## 5. 结果不对：利用确定性在本地重放

这是本项目最大的优势。同一个请求 + 同一个 seed + 同一个引擎版本，结果一定逐字节相同（第 17 课实测过跨线程也成立）。所以：

1. 线上发现某场战斗结果异常 → 从日志里取出这场战斗的**请求原始字节**（ETF）和引擎版本；
2. 在本地用同一个版本的引擎加载这份字节，用 `-O0 -g` 构建，结果一定和线上完全一样；
3. 在 gdb 里给 `EffectSystem::apply_damage` 加条件断点（比如 `break apply_damage if target_index == 3`），一步步看。

`practice/battle_bench.cpp` 的 `--dump-request` 就是把一个请求保存成 ETF 文件的例子。线上建议：**所有返回错误或触发报警的战斗，都把请求字节存下来**。

## 6. 模糊测试

单元测试检查"我想到的输入"，模糊测试（fuzzing）检查"我没想到的输入"：自动生成大量畸形数据喂给程序，看它会不会崩溃，或者触发 sanitizer 报错。

`wire::handle_etf` 是整个引擎对外的唯一入口：Port 和 NIF 收到的每一个字节都会经过它。它必须做到：**任何输入都只返回 `{ok, _}` 或 `{error, _}`，绝不崩溃，也不触发未定义行为**。尤其是 NIF 模式下，这里一崩溃就是整个 Erlang 节点崩溃。

### 测试入口

```cpp
extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    const auto reply = gamebattle::wire::handle_etf({data, size});   // 任何输入都要正常返回
    const auto decoded = gamebattle::term::decode(reply);            // 自己的回复必须总能解码
    return 0;
}
```

这是 libFuzzer 的标准入口函数。有 libFuzzer 的环境下，用 `clang++ -fsanitize=fuzzer,address,undefined` 编译即可，libFuzzer 会根据代码覆盖率自动变异输入，比随机变异聪明得多。

这台机器的 clang 缺少 libFuzzer 运行时，所以 `term_fuzz.cpp` 自带了一个简单的变异驱动：从几份合法的种子输入（示例战斗请求、`ping`、`load_config` 命令、混合类型的列表）出发，随机组合以下变异方式：
- 翻转某一位；
- 把某个字节改成"有意思的值"：0、0xFF、各种 ETF 类型标签；
- 截断；插入随机字节；
- 从另一份种子里截取一段拼接进来；
- **把某 4 个字节改成极端的长度值**：0、1、0x7FFFFFFF、0xFFFFFFFF、1000000。

### 实测结果

用 AddressSanitizer + UBSan 构建，跑 20 万次：

```
iterations: 200000 in 154 s, no crash
sampled outcomes:
  error:config_load_failed: 65
  error:invalid_request: 3001
  ok: 59
```

20 万个畸形输入，没有任何崩溃、内存错误或未定义行为。绝大多数被正确地判定为 `invalid_request`，少数变异后仍然合法的请求正常返回 `ok`。这说明 `term.cpp` 的防御性写法（第 9 课：每次读取前检查长度、限制嵌套深度和元素个数）是有效的。

**但"没崩溃"不等于"没问题"**，下一节就是一个随机模糊测试很难发现的问题。

## 7. 本课程过程中发现的真实问题

编写这套课程的实战代码时，我在引擎里发现了两个真实的问题（加上第 21 课的性能问题，一共三个）。`practice/known_issues.cpp` 能复现它们，并报告是否已修复。当前的运行结果：

```
[1] same inline buff on two units
    Engine::simulate (in process): ok
    wire::handle_etf (over ETF)  : error invalid_request: one battle request contains conflicting definitions for a buff id
[2] 501-byte input of nested lists
    reply: error invalid_request: truncated ETF value
    VmPeak grew by 3814 MB

issue 1 (inline buff conflict)        : PRESENT
issue 2 (nested reserve amplification): PRESENT
issue 3 (slow result encoding)        : run encode_bench to compare
```

### 问题 1：两个单位带同一个内联 Buff，请求被拒绝

**怎么发现的**：写第 21 课的基准测试时，需要把 C++ 里构造的请求转成 ETF 走完整链路。同一个请求，直接调用 `Engine::simulate` 正常，经过 ETF 就被拒绝。

**根本原因**：
- `wire.cpp:313` 解析内联 Buff 时，**每遇到一次**就 `std::make_shared<BuffSpec>(...)` 新建一个对象。两个单位都带"淬毒"被动，就产生了两个内容相同、地址不同的 `BuffSpec`。
- `battle_state.cpp:166-170` 的校验用 `buff_id → 指针` 记录见过的 Buff，同一个 id 对应了**不同的指针**就判定为"冲突的定义"。它用"指针不同"来代表"定义不同"，而这个前提对内联请求不成立。
- 直接在 C++ 里构造请求时，两个单位共享同一个 `shared_ptr`，所以不会触发。通过配置 ID（`skill_ids`）发来的请求，Buff 来自 `ConfigStore`，也是共享的同一个对象，同样不受影响。

**影响**：只影响**内联格式**的请求，而且要两个单位带同一个 id 的 Buff。README 的示例请求里每个 Buff 只出现在一个单位上，所以没有暴露。线上推荐的配置 ID 方式不受影响。但"三个英雄都带同一个被动"在内联格式下是非常自然的写法，会被莫名拒绝。

**修复思路**（任选其一）：
1. `parse_request` 在解析过程中维护一个 `buff_id → shared_ptr` 的表：同一个 id 第二次出现时，**内容相同就复用第一次的对象**，内容不同才报错。需要给 `BuffSpec`、`BuffReaction`、`Effect` 写深比较（注意 `Effect::buff` 是 `shared_ptr`，默认的 `operator==` 只比较指针，要比较的是指向的内容）。
2. 改 `validate_request`：指针不同时，进一步比较内容。

方案 1 更好：解析后同一个 Buff 只有一份对象，内存更省，和配置 ID 路径的行为也一致。

### 问题 2：501 字节的输入让进程预留了 3.8 GB 内存

**怎么发现的**：读 `term.cpp` 时注意到，解码列表时 `check_count` 只检查元素个数不超过 100 万，然后立即 `list.reserve(count)`。这时还没有确认输入里真的有那么多数据。

**复现**：构造 100 层嵌套的列表，每一层都声称有 1,000,000 个元素（每层只需要 5 个字节）：

```
501-byte input of nested lists
reply: error invalid_request: truncated ETF value
VmPeak grew by 3814 MB                        ← 嵌套 map 版本是 7.0 GB
```

每一层 `reserve` 了 100 万个 `Value`（约 40 MB），递归 100 层。最终因为数据不够而返回"截断"错误，栈展开时这些内存都被释放了。

**为什么平时看不出来**：Linux 默认的内存过量分配策略下，`reserve` 只分配虚拟地址，没有真正写入的页面不占物理内存，所以常驻内存（RSS）只有 4 MB，进程也没有崩溃。随机模糊测试也没发现它，因为随机变异几乎不可能凑出"100 层嵌套、每层都是最大计数"这种结构，而且它不会触发 sanitizer 报错。

**什么时候会出事**：进程设置了地址空间上限时（容器或者一些加固过的环境会这样做）。实测 `ulimit -v 2000000`（2 GB）下：

```
reply: error / std::bad_alloc
VmPeak: 1998924 kB                ← 整个地址空间上限被一个请求占满
```

- 错误类型变成了 `internal_error`，而不是 `invalid_request`（第 8 课的分类被打乱了）；
- 在这个瞬间，**同一进程里的其他内存分配都会失败**。Port 模式下影响有限；NIF 模式下，BEAM 虚拟机的其他线程如果恰好在这时分配内存，可能导致整个 Erlang 节点崩溃。

**修复**：每个元素至少占 1 个字节，所以预留的个数不应该超过剩余的字节数：

```cpp
list.reserve(std::min<std::size_t>(count, bytes_.size() - offset_));   // 列表、元组
object.reserve(std::min<std::size_t>(count, (bytes_.size() - offset_) / 2));   // map：每对至少 2 字节
```

改完后重新运行 `known_issues`，第 2 项应该显示 `fixed`。

**经验**：
- 外部输入里的"长度""个数"字段，在**分配内存之前**要和"实际剩余的数据量"比较，而不只是和一个固定上限比较；
- libFuzzer 有 `-malloc_limit_mb` 参数，可以把"单次分配超过 N MB"当成错误报告出来，专门用来发现这类问题；
- 模糊测试之外，**带着攻击者的视角读代码**同样重要。

### 两个更小的隐患（前面课程已经提到过）

- `nif.cpp` 的 `enif_release_binary` 是手动调用的，没有 RAII 保护（第 9 课），可以用 `unique_ptr` 加自定义删除器解决（第 14 课）。
- `handle_etf` 的 catch 块里还会分配内存（第 8 课）。极端情况下（内存耗尽）会从 catch 块里再次抛出异常，NIF 模式下会导致节点崩溃。

这几个问题都**留给你自己修复**：修复、补上测试、提交，这正是第 24 课要讲的"简历上可验证的项目经历"。

## 8. 日志与监控

出了问题能不能查清楚，取决于事前留下了什么：

- **每场战斗都带 `battle_id`、`seed`、引擎版本**。出错的战斗把请求原始字节保存下来。
- **把 Port 的退出码翻译成可读的原因**：0 正常退出，2~5 是 `port_main.cpp` 里定义的协议错误（第 9 课），134 是 `abort`（比如未捕获的异常，第 8 课），139 是段错误。
- **指标**：每秒战斗数、延迟的 p50/p99、错误率（按 `invalid_request` / `internal_error` 分开统计）、Port 重启次数。`internal_error` 一出现就该报警。
- **崩溃时自动保留现场**：开启 core dump，归档每个版本的调试符号。

## 面试题

**Q1：线上 C++ 服务崩溃了，你怎么排查？**
先看退出码或信号（139 是段错误、134 是 abort）。开启 core dump，用 `gdb 程序 core` 查看崩溃线程的调用栈，`thread apply all bt` 看所有线程。线上用 `-O2 -g` 构建并归档分离出来的调试符号（用 Build ID 对应版本）。遇到 `<optimized out>` 时结合日志，在本地用相同输入以 `-O0` 复现。

**Q2：程序卡死了怎么查？**
`gdb -p PID` 附加到进程，`thread apply all bt` 看每个线程停在哪里。多个线程都停在 `mutex::lock`、等待不同的锁，就是死锁。不能停服务时，用 `gcore` 生成 core 文件事后分析。

**Q3：怎么排查内存泄漏？**
开发阶段用 AddressSanitizer / LeakSanitizer；不能重新编译时用 valgrind memcheck（实测能定位到 `shared_ptr` 环形引用泄漏的那一行）。内存持续增长但没有泄漏时，用 heaptrack 或 massif 分析是谁在增长：可能是无上限的缓存、堆积的队列或碎片。

**Q4：什么是模糊测试？你是怎么做的？**
自动生成大量畸形输入，检查程序是否崩溃或触发 sanitizer。我针对引擎唯一的外部入口 `wire::handle_etf` 写了兼容 libFuzzer 的测试函数和一个变异驱动，在 ASan + UBSan 下跑了 20 万次，没有崩溃。另外通过代码审查发现了一个随机模糊测试很难触发的问题：嵌套容器在确认数据存在之前就按声明的个数预分配，501 字节的输入能让虚拟内存峰值增长 3.8 GB。

**Q5：说一个你发现并分析过的 Bug。**
（问题 1 或问题 2，按"现象 → 复现 → 根本原因 → 影响范围 → 修复方案 → 验证"的顺序讲。）比如问题 1：同一个请求直接调用引擎正常，经过 ETF 却被拒绝；原因是解析时每个内联 Buff 都新建对象，而校验代码用"指针不同"判定"定义冲突"；只影响内联格式且多个单位带同一 Buff 的请求；修复方案是解析时按 id 去重并比较内容；用 `known_issues` 程序作为回归测试。

**Q6：为什么一定要用 Release 加调试符号的方式发布？**
纯 Release 没有符号，core 文件里只有地址，无法定位到源码；纯 Debug 慢几十倍，不能用于线上。`-O2 -g` 再分离符号，线上程序体积小、速度快，出问题时用归档的符号文件分析。
