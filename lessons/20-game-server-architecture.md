# 第 20 课：游戏服务器架构与常用数据结构

> 实战代码：`practice/ds/`（跳表排行榜、时间轮、九宫格 AOI、一致性哈希、AoS/SoA 对比），全部带正确性校验和实测数据。
>
> 游戏服务端面试除了 C++ 本身，一定会问"你们的服务器是怎么划分的""战斗怎么同步""排行榜怎么做""定时器怎么实现"。这一课把这些高频题和本项目串起来。

## 1. 典型的游戏服务器进程划分

```
               ┌──────────┐
  客户端 ─────▶│  网关     │  维持长连接、加解密、协议编解码、限流
               └────┬─────┘
       ┌────────────┼──────────────┬──────────────┐
       ▼            ▼              ▼              ▼
  ┌─────────┐ ┌──────────┐  ┌────────────┐ ┌───────────┐
  │ 登录/账号 │ │ 逻辑/场景 │  │ 匹配 / 社交 │ │ 聊天      │
  └─────────┘ └────┬─────┘  └────────────┘ └───────────┘
                   │  战斗请求（battle_id、双方阵容、seed）
                   ▼
            ┌──────────────┐
            │ 战斗服务 ◀── 本项目：Port / NIF / TCP 战斗服务器（第 19 课）
            └──────┬───────┘
                   │  战斗结果 → 结算
                   ▼
            ┌──────────────┐      ┌────────┐
            │ 数据代理/缓存 │─────▶│ MySQL  │  持久化
            │   (Redis)    │      └────────┘
            └──────────────┘
```

国内不少游戏公司的常见组合是：**Erlang 写网关、逻辑、社交这类连接多、状态多、要求高可用的服务**；**C++ 写战斗、场景、寻路这类计算密集的服务**。你同时掌握 Erlang 和 C++，正好可以讲清楚两边怎么分工、怎么对接（Port、NIF、TCP 三种方式各自的取舍，第 9、19 课），这是很有竞争力的一点。

## 2. 战斗怎么同步：三种模式

| 模式 | 做法 | 适合 | 对确定性的要求 |
|---|---|---|---|
| **服务器权威结算**（本项目） | 客户端只提交阵容和指令，服务器算完整场战斗，把事件流发给客户端播放 | 回合制、卡牌、放置类 | 服务器自己可复现即可 |
| **状态同步** | 服务器运行游戏逻辑，定期把各实体的状态（位置、血量……）广播给客户端 | MMO、射击类 | 低：客户端只是显示 |
| **帧同步（锁步）** | 服务器只转发每一帧所有玩家的输入，每个客户端各自运行完全相同的逻辑 | MOBA、RTS、格斗 | **极高**：所有客户端必须算出完全相同的结果，差一点就"不同步" |

帧同步和战报回放对确定性的要求，和本项目已经做到的完全一致。回顾一下前面讲过的所有保证措施：

| 要求 | 做法 | 课 |
|---|---|---|
| 不用浮点数 | 全部用整数和基点 | 第 5、7 课 |
| 跨平台一致的随机数 | 自己实现 SplitMix64，不用标准库的分布 | 第 3 课 |
| 不依赖未定义的顺序 | 不遍历 `unordered_map`；排序最后一定比较唯一 ID | 第 1、5 课 |
| 没有未定义行为 | 饱和运算，不让有符号数溢出 | 第 7 课 |
| 多线程不影响结果 | 每场战斗状态独立 | 第 17 课（实测 4 线程结果逐字节相同） |

### 确定性带来的直接收益：存请求，而不是存结果

本项目的实测数据：一场 5v5 战斗的**请求**编码后是 8.6 KB，**结果**（912 个事件）是 148 KB。如果要保存战报供玩家回看，只需要保存"请求 + 引擎版本号"，播放时重新计算一遍，存储空间**减少约 17 倍**。

同样的思路还能用于**反作弊**：客户端上报"我赢了"，服务器拿同样的输入重新算一遍，结果不一致就是作弊或客户端被篡改。

前提是第 3 课强调过的：**引擎版本必须一致**。只要改动了任何一次随机判定，旧的请求就算不出旧的结果。所以战报里一定要记录引擎版本，服务器要能找到对应版本的引擎。

## 3. 定时器：最小堆 vs 时间轮

游戏服务器里到处是定时器：Buff 到期、技能冷却、活动开始、断线超时、心跳检测……可能同时存在几十万个。

**最小堆**（`std::priority_queue`）：按到期时间排序，每次只看堆顶。插入、弹出都是 O(log n)。

**时间轮**：把时间切成固定的格子（比如每格 10 ms），排成一个环。定时器按到期时间放进对应的格子，每个 tick 只处理当前那一格：

```
          tick 指针每 10 ms 前进一格
                 │
   ┌───┬───┬───┬─▼─┬───┬───┬─── ... ───┐
   │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │   1023    │   1024 个槽，一圈 10.24 秒
   └───┴───┴───┴─┬─┴───┴───┴─── ... ───┘
                 └─▶ [定时器 A, rounds=0] [定时器 B, rounds=2]   超过一圈的记录还要再转几圈
```

插入是 O(1)；每个 tick 只处理一个槽。实测 100 万个定时器，到期时间随机分布在 1~30000 个 tick 之间（`practice/ds/timers.cpp`）：

```
最小堆  : 插入 36 ms, 推进并触发 506 ms
时间轮  : 插入 26 ms, 推进并触发 103 ms
两者在完全相同的 tick 触发了完全相同的定时器: 1
```

触发阶段时间轮快约 **5 倍**，而且程序用校验和验证了两种实现的触发时刻完全一致。

- 延迟跨度很大时（几毫秒到几天），单层时间轮里"还要转很多圈"的定时器会被反复扫描。工业实现用**多层时间轮**（像时钟的秒针、分针、时针）：Linux 内核、Kafka、Netty 都是这样做的。
- **取消定时器**：时间轮可以让每个定时器带一个句柄，取消时直接从槽里删除（用侵入式链表就是 O(1)）；最小堆不方便删除中间元素，常用"打标记，弹出时跳过"的懒删除。
- Erlang 虚拟机的定时器（`erlang:send_after`、`receive ... after`）内部也是基于时间轮实现的。

## 4. AOI：只把附近的东西告诉玩家

AOI（Area of Interest，兴趣区域）：MMO 里一个玩家只需要知道视野范围内的其他玩家和怪物。最直接的做法是每次遍历所有实体算距离，O(N)。

**九宫格**：把地图切成边长等于视野半径的格子，每个格子记录里面有哪些实体。查询时只需要看自己所在的格子和周围 8 个格子：

```
┌────┬────┬────┐
│    │    │    │
├────┼────┼────┤      视野半径 = 格子边长
│    │ 我 │    │      只需要检查这 9 个格子
├────┼────┼────┤
│    │    │    │
└────┴────┴────┘
```

实测 2 万个实体、2 万次视野查询（`practice/ds/aoi.cpp`）：

```
暴力遍历: 400.7 ms
九宫格  : 2.8 ms
两种方法找到的实体总数相同: 1 (125096)
```

快了约 **140 倍**，而且结果完全一样。

实际的 AOI 系统还要处理**进入和离开视野的事件**：实体移动后，比较新旧两次的视野集合，多出来的发"进入"，少了的发"离开"。另一种常见实现是**十字链表**：按 x 坐标、y 坐标各维护一个有序链表，适合实体分布非常不均匀的地图。

## 5. 排行榜：跳表

需求：几十万到几百万玩家，分数频繁变化，要能快速回答"我排第几名"和"第 100 名是谁"。

`std::set` 能按分数排序，但它求排名只能从头一个个数（`std::distance`），O(n)。

**Redis 的 ZSET** 用的是**跳表 + 哈希表**。跳表是一个多层的有序链表，上层是下层的"快速通道"：

```
第 3 层: head ──────────────────────────▶ 90 ──────────────────────▶ nil
第 2 层: head ─────────▶ 120 ───────────▶ 90 ─────────▶ 60 ────────▶ nil
第 1 层: head ─▶ 150 ─▶ 120 ─▶ 100 ─▶ 95 ─▶ 90 ─▶ 80 ─▶ 60 ─▶ 40 ─▶ nil
```

每个节点随机决定自己有几层（每升一层的概率是 1/4），查找时从最高层开始，能跳就跳，期望 O(log n)。**关键技巧**：每个前进指针额外记录一个 `span`，表示这一步跳过了几个节点。查找时把走过的 `span` 加起来，就得到了排名。

`practice/ds/ranklist.hpp` 实现了一个和 Redis 同样思路的跳表（约 150 行），支持插入、删除、按 (分数, id) 查排名、按排名查 id。实测：

```
6 万次随机增删改，8571 次排名查询与 std::set 结果完全一致
20 万玩家：跳表查一次排名 2.0~2.5 us，std::set + distance 查一次 18000 us
```

正确性用 `std::set` 作为参照逐一比对，并在 AddressSanitizer + UBSan 下跑过。性能上，20 万玩家时差了约 **8000 倍**。

面试时常见的追问：
- **为什么 Redis 用跳表而不用红黑树？** 跳表实现简单得多；范围查询（"第 100~200 名"）只需要找到起点再沿底层链表走；求排名只需要 `span` 字段，红黑树要额外维护子树大小。
- **同分怎么排？** 本实现按 id 从小到大，保证排序是全序、结果确定（第 5 课的规则）。也可以按"先达到这个分数的排前面"，那就把时间戳编码进分数里。
- **上亿玩家怎么办？** 一般不需要精确排名：前 1 万名用跳表精确维护，后面的按分数分桶统计人数，给出"超过了 87% 的玩家"这种近似排名。

## 6. 一致性哈希：战斗服务器怎么分片

有 3 台战斗服务器，按 `battle_id` 选一台。最简单的是 `hash(battle_id) % 3`。问题是扩容到 4 台后，`% 4` 的结果几乎全变了。如果服务器上有缓存或者有状态（比如连续的车轮战要落在同一台上），就会大面积失效。

**一致性哈希**：把服务器和 key 都哈希到一个环上，key 顺时针找到的第一个服务器就是它的归属。加一台服务器只会抢走它在环上"前一段"的 key。

```cpp
class HashRing {
    std::map<std::uint64_t, int> ring_;            // 环上的位置 → 服务器
public:
    void add(int server) {
        for (int v = 0; v < virtual_nodes_; ++v) ring_[mix((server << 32) | v)] = server;   // 每台服务器放多个虚拟节点
    }
    int pick(std::uint64_t battle_id) const {
        auto it = ring_.lower_bound(mix(battle_id));   // 顺时针第一个节点：std::map 的有序性正好派上用场
        return it == ring_.end() ? ring_.begin()->second : it->second;
    }
};
```

实测 30 万场战斗（`practice/ds/consistent_hash.cpp`）：

```
一致性哈希(每台 1 个虚拟节点):   3 台时分布 35029/258472/6499，加第 4 台后迁移 40.5% 的战斗
一致性哈希(每台 160 个虚拟节点): 3 台时分布 94458/103955/101587，加第 4 台后迁移 24.1% 的战斗
取模 hash % N: 从 3 台变 4 台迁移 74.9% 的战斗
```

- 取模方式迁移了 75% 的 key；一致性哈希只迁移 24%，接近理论最优值 25%（新服务器应该分走四分之一）。
- **虚拟节点**非常关键：每台只放 1 个节点时，环上的间隔很不均匀，一台服务器承担了 86% 的流量。每台放 160 个虚拟节点后，三台的负载基本均衡。

## 7. 面向数据的设计与 ECS

第 16 课提到 `sizeof(Event)` 是 136 字节。如果一次只需要处理其中的一个字段，CPU 却要把整个 136 字节读进缓存，大部分带宽都浪费了。

实测 200 万个单位，每轮把所有单位的 hp 减 1，共 20 轮（`practice/ds/aos_soa.cpp`）：

```
sizeof(UnitAoS)=144
AoS（结构体数组）       : 377 ms
SoA（每个字段一个数组）  : 29 ms   结果一致: 1
```

**快了约 13 倍**。

- **AoS**（Array of Structures）：`vector<Unit>`，一个单位的所有字段挨在一起。面向对象的自然写法。
- **SoA**（Structure of Arrays）：每个字段一个数组，同一个字段的所有值挨在一起。只处理 hp 时，读进缓存的每个字节都是有用的，编译器还能用 SIMD 指令一次处理多个值。

**ECS**（Entity-Component-System）是把这个思路系统化的架构，在游戏客户端和服务器里都很流行：
- **Entity**：只是一个 ID；
- **Component**：纯数据（位置、血量、移动速度……），同类组件存在连续数组里；
- **System**：遍历拥有某几种组件的实体，执行一种逻辑（移动系统、战斗系统、Buff 系统）。

这和第 12 课讨论的"为什么不用虚函数继承体系"是同一个方向：**按数据怎么被访问来组织数据，而不是按"它是什么东西"来组织**。本项目的战斗规模只有十个单位左右，AoS 完全没问题；但在一个几千个实体的 MMO 场景里，这个差别就决定了一台服务器能承载多少玩家。

## 8. 热更新

| 层次 | 做法 | 本项目 |
|---|---|---|
| 配置 | 重新加载配置文件，原子地切换指针，已经开始的请求用旧配置 | ✅ `load_config`（第 10 课） |
| 脚本逻辑 | 业务逻辑用 Lua 等脚本写，C++ 提供引擎接口，重新加载脚本即可更新逻辑 | 未使用 |
| 本地代码 | `dlopen` 加载新版本的动态库；但已有对象的虚表、静态变量、正在执行的函数都可能出问题，风险很高 | 未使用 |
| 进程级 | 新版本进程启动后接管流量，旧进程处理完存量请求再退出 | Port 模式下重启 Port 进程就是这种方式 |

Erlang 天生支持代码热加载（同一模块的新旧两个版本可以同时运行），这是 Erlang 在游戏服务端很受欢迎的原因之一，也是 C++ 很难做到的地方。面试时能讲清楚这个对比，是你的优势。

## 9. 存储与结算

- **Redis 做缓存，MySQL 做持久化**：玩家数据加载到内存（或 Redis）里修改，标记为"脏"，定期或在下线时批量写回 MySQL。
- **结算必须幂等**：网络超时后，客户端或逻辑服可能会重发同一场战斗的结算请求。用 `battle_id` 做唯一键，保证同一场战斗只结算一次。本项目的车轮战（`gamebattle_gauntlet.erl`）在中途出错时返回已完成的结果和最后一份 `carryover`，用于断点续打，也是同样的思想。
- **先写日志，再改状态**：涉及道具、货币的操作，先写入流水日志，再修改玩家数据；崩溃恢复时以日志为准。

## 面试题

**Q1：介绍一下你们的服务器架构。**
（结合第 1 节作答）网关维持长连接，逻辑服处理玩家业务，战斗作为独立服务；战斗服务只接收"阵容 + seed"，返回事件流和结果。Erlang 负责连接和业务逻辑，C++ 负责战斗计算，支持 Port、NIF、TCP 三种接入方式。

**Q2：状态同步和帧同步的区别？帧同步要注意什么？**
状态同步由服务器计算并广播状态，客户端只负责显示；帧同步只同步输入，各客户端各自运行相同的逻辑。帧同步要求严格的确定性：不能用浮点数（或要用定点数）、随机数要用相同的算法和种子、不能依赖哈希表遍历顺序、不能有未定义行为。

**Q3：游戏里的定时器怎么实现？**
少量定时器用最小堆即可，插入和弹出 O(log n)。大量定时器用时间轮，插入 O(1)，每个 tick 只处理一个槽；延迟跨度大时用多层时间轮。实测 100 万个定时器，时间轮触发阶段比最小堆快约 5 倍。

**Q4：AOI 怎么实现？**
九宫格：地图切成边长约等于视野半径的格子，查询时只看周围 9 个格子；实测比暴力遍历快约 140 倍。也可以用十字链表。还要根据新旧视野集合的差异，生成进入、离开视野的事件。

**Q5：排行榜怎么实现？为什么 Redis 用跳表？**
跳表 + 哈希表：哈希表按玩家 id 找到当前分数，跳表按分数排序，指针上的 `span` 字段用来 O(log n) 求排名。跳表比红黑树实现简单，范围查询方便。实测 20 万人时跳表查一次排名约 2 µs，`std::set` 数过去要 18 ms。

**Q6：一致性哈希是什么？为什么要虚拟节点？**
把节点和 key 都映射到一个哈希环上，key 归属顺时针方向的第一个节点；增删节点只影响相邻的一段。虚拟节点让每台机器在环上占多个位置，使负载均匀。实测加第 4 台服务器只迁移 24% 的 key（取模方式迁移 75%）；没有虚拟节点时一台服务器承担了 86% 的流量。

**Q7：什么是 ECS？为什么 SoA 比 AoS 快？**
实体只是 ID，组件是存放在连续数组里的纯数据，系统遍历拥有特定组件的实体执行逻辑。SoA 让同一字段的数据连续存放，只处理某个字段时缓存利用率高，也便于 SIMD。实测只更新一个字段时 SoA 比 AoS 快约 13 倍。

**Q8：战斗回放怎么做？**
如果战斗逻辑是确定性的，只需要保存输入（阵容、seed）和引擎版本，回放时重新计算即可。本项目中请求 8.6 KB、结果 148 KB，可以省约 17 倍存储空间；同样的机制可以用于反作弊校验。前提是必须保留对应版本的引擎。

**Q9：结算请求重复了怎么办？**
以 `battle_id` 作为唯一键做幂等：结算前检查是否已经处理过，处理结果与流水日志在同一个事务里写入。
