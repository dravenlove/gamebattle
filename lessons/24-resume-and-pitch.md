# 第 24 课：简历与项目讲述

> 最后一课。前 23 课解决"懂不懂"，这一课解决"怎么让面试官相信你懂"。

## 1. 先说清楚：这套课程能给你什么，不能给你什么

**能给你的**：
- 一个有深度、能被追问的项目：确定性战斗引擎 + Erlang 三种接入方式 + 配置管线 + 线程池 + epoll 服务器 + 性能分析 + 模糊测试；
- 每个设计决定背后的原因，以及几十组可以在面试中引用的实测数据；
- 覆盖 C++ 游戏服务端岗位主要考点的知识体系和题库（第 23 课）。

**不能替你做的**：
- **算法题**：需要单独刷（第 23 课 N 部分）。
- **亲手写代码的肌肉记忆**：读懂和写出来是两回事，面试可能让你现场写一个线程池或 LRU。
- **项目的"所有权"**：这一点最重要，单独说。

### 关于项目是谁写的

这个引擎最初是你和 Codex 一起生成的，课程里的实战代码是我写的。面试官看到简历上的项目，一定会顺着往下问：为什么这么设计？这里如果并发访问会怎样？你遇到的最难的问题是什么？如果你只是"读过"这些代码，三个追问之内就会露馅。

所以两条原则：

1. **简历上只写你能讲清楚每一个细节的内容。** 这套课程的目的，就是让你能讲清楚引擎里的每一行。
2. **让项目真正成为你的。** 下一节列出的修复和扩展，请你**自己动手**完成并提交。这样你讲的每一个问题都是你亲手定位、修复、验证过的，面试时自然经得起追问。

用 AI 辅助开发本身不是问题，现在很多团队都这么做。问题在于你是否理解、能否掌控这些代码。如果面试官问起，可以坦然地说："初始版本用 AI 辅助生成，之后我系统地审读了全部代码，发现并修复了几个问题，做了性能分析和优化。"这比假装全部自己从零写出来更可信，也更能体现工程能力。

## 3. 简历怎么写

### 项目描述（2~3 行）

> **Erlang 可调用的 C++20 确定性战斗引擎**
> 回合制战斗服务端核心：数据驱动的技能 / 被动 / Buff 系统，同一输入与随机种子保证结果逐字节一致（用于战报回放与反作弊）；支持 Erlang Port、NIF、TCP 三种接入方式；配套 CSV → 二进制配置编译器，支持不停服热更新。

### 成果要点（按你实际完成的情况选用和修改）

下面的数字来自这套课程在一台 4 核云虚拟机上的实测。**写进简历之前，请在你自己的机器上重新测量**，用你自己测到的数字：

- **性能**：编写覆盖完整链路的分段基准测试，定位到结果编码占约 78% 耗时；用 callgrind 分析出 `std::initializer_list` 导致事件列表被深复制；优化后编码快约 1.9 倍（流式编码器方案约 4 倍），单线程吞吐从约 900 场/秒提升到约 1700 场/秒，修改前后输出经逐字节对比验证一致。
- **并发**：实现线程池并发执行战斗，4 核加速约 3.5 倍，与单线程结果逐字节一致，ThreadSanitizer 无数据竞争。
- **网络**：基于 Linux epoll 实现 Reactor + 工作线程池的 TCP 战斗服务，长度前缀分帧（兼容 Erlang `gen_tcp` 的 `{packet, 4}`）、按连接保序、背压控制、`signalfd` 优雅退出；单连接 p50 延迟约 2.1 ms、p99 约 4.2 ms。
- **质量**：为 ETF 协议入口编写模糊测试，在 ASan + UBSan 下运行 20 万次无崩溃；通过代码审查发现并修复一个内存放大问题（501 字节输入导致虚拟内存峰值增长 3.8 GB）和一个内联 Buff 被误判冲突的问题。
- **工程**：搭建 CI，自动运行单元测试、sanitizer 构建和模糊测试。

### 技能栏

把课程覆盖的内容写成面试官能检索到的关键词：C++17/20（移动语义、智能指针、模板与 concepts、`std::variant`）、STL 原理、多线程（mutex / 条件变量 / atomic / 内存序 / 无锁队列）、Linux 网络编程（epoll / Reactor）、CMake、gdb / core dump、AddressSanitizer / ThreadSanitizer / valgrind、性能分析（callgrind / perf）、Erlang/OTP（gen_server、监督树、Port / NIF）。

**写上去的每一个词，都要准备好被追问。** 第 23 课的题库就是按这个思路组织的。

## 4. 三个可以反复讲的故事

面试中的项目追问，用 **STAR** 结构回答：情境（Situation）、任务（Task）、行动（Action）、结果（Result）。下面三个故事覆盖了"性能""排查问题""设计与并发"三类最常见的追问。

> 故事里的"修复""优化后"，**以你已经亲手完成第 2 节动手清单中对应的任务为前提**。没做完之前，只能说"发现了、分析了、提出了修复方案"，不能说"已修复"。

### 故事一：把吞吐量翻倍的性能分析（第 21 课）

- **情境**：引擎通过 Erlang Port 提供服务，我想知道单个 Port 进程每秒能处理多少场战斗、瓶颈在哪里。
- **任务**：找出瓶颈并在不改变任何输出的前提下优化。
- **行动**：
  1. 写了一个基准程序，把完整链路拆成解码、解析、模拟、编码四段分别计时，用 3000 场不同 seed 的战斗测试。结果出乎意料：模拟只占 15%，**编码结果占了 78%**。
  2. 用 valgrind 的 callgrind 分析，发现 30% 以上的指令花在 `vector` 的复制构造函数上。
  3. 读代码找到原因：用 `std::initializer_list` 构造嵌套的 map 时，元素是 `const` 的，只能复制，整个事件列表被深复制了一遍。
  4. 写了两种替代实现：去掉复制的版本，以及不建中间结构、直接流式写字节的版本。**先验证 1000 场战斗的输出逐字节相同**，再计时。
- **结果**：编码分别快约 1.9 倍和 4 倍，完整链路单线程吞吐从约 900 提升到约 1700 场/秒。考虑到维护成本，我先采用了改动更小的方案。

**可能的追问**：
- *为什么不一开始就优化模拟部分？* → 阿姆达尔定律：模拟只占 15%，优化到零也只快 1.18 倍。
- *怎么保证优化没改坏结果？* → 逐字节对比，而且对比测试长期保留在代码里。
- *测量结果可信吗？* → Release 构建、预热、多次运行；我还遇到过两次"被优化器删掉"的假数据，都通过换算"每次操作几个时钟周期"识别出来了（第 21 课）。
- *`initializer_list` 为什么只能复制？* → 第 13 课第 6 节。

### 故事二：一个 501 字节的请求（第 22 课）

- **情境**：引擎对外的唯一入口是 ETF 解码。NIF 模式下它运行在 Erlang 虚拟机内部，一旦出问题，整个节点都会受影响。
- **任务**：确认这个入口对任何输入都是安全的。
- **行动**：
  1. 写了模糊测试，在 ASan + UBSan 下跑了 20 万次，没有发现崩溃。
  2. 但我继续带着攻击者的视角读解码代码，注意到解码列表时只检查了元素个数的上限（100 万），就按这个个数预分配内存，而这时还没确认输入里真有那么多数据。
  3. 构造了一个 100 层嵌套、每层声称 100 万个元素的输入，只有 501 字节。实测进程的虚拟内存峰值增长了 3.8 GB（map 版本 7 GB）。
  4. 分析影响：默认配置下物理内存不受影响，但在设置了地址空间上限的环境里，实测请求会耗尽整个上限、返回被错误分类的 `internal_error`，NIF 模式下还可能连带 BEAM 其他线程的内存分配失败。
  5. 修复：预分配的个数不超过剩余字节数（每个元素至少 1 字节）。
- **结果**：回归测试程序确认修复；模糊测试全部通过。我也总结了一条经验：外部输入里的长度字段，在分配内存之前要和实际剩余的数据量比较。

**可能的追问**：
- *为什么模糊测试没发现？* → 随机变异很难凑出这种深层结构，而且它不触发 sanitizer，物理内存也不增长。libFuzzer 的 `-malloc_limit_mb` 可以专门捕捉这类问题。
- *虚拟内存和物理内存的区别？* → 第 23 课第 80 题。
- *为什么 NIF 模式下更危险？* → 第 8、9 课。

### 故事三：确定性与并发（第 3、5、7、17、20 课）

- **情境**：战斗结果要能回放、要能被服务器重算校验，而且要能多线程并发计算。
- **任务**：保证同一个请求在任何平台、任何线程上都得到完全相同的结果。
- **行动**：讲清楚每一类不确定性的来源和对应的措施：浮点数 → 全部用整数和基点；标准库随机数分布不跨平台 → 自己实现 SplitMix64；`std::sort` 不稳定 → 比较函数最后比较唯一 ID；哈希表遍历顺序 → 不遍历 `unordered_map`；有符号溢出是未定义行为 → 饱和运算；多线程 → 每场战斗的状态完全隔离，共享配置只读。
- **结果**：线程池 4 个线程并发跑 2000 场，结果与单线程逐字节相同，加速约 3.5 倍，ThreadSanitizer 无警告。基于确定性，战报只需要存请求（8.6 KB）而不必存结果（148 KB）。

**可能的追问**：
- *改了代码以后旧战报还能回放吗？* → 不一定，任何新增的随机判定都会让后续随机数错位，所以战报要记录引擎版本（第 3 课）。
- *为什么错误的内存序在测试里不出问题？* → 第 18 课。
- *为什么线程数增加到 4 加速不到 4 倍？* → 主线程争用、分配器竞争；空任务调度开销的实测数据（第 17 课）。

## 5. 一分钟版和三分钟版的项目介绍

**一分钟版**（自我介绍时用，同样以完成动手清单为前提）：

> 我主要做 Erlang 游戏服务端，最近在做一个用 C++20 写的回合制战斗引擎，Erlang 可以通过 Port、NIF 或 TCP 调用它。核心特点是确定性：同一个输入和随机种子，在任何平台、任何线程上结果都逐字节一致，所以能做战报回放和反作弊校验。我在这个项目上做了性能分析，把单线程吞吐提升了将近一倍；也写了模糊测试，发现并修复了一个能让 501 字节的请求占用几 GB 虚拟内存的问题。

**三分钟版**（"介绍一下你的项目"时用）：按"架构 → 一个设计亮点 → 一个问题和解决过程 → 数据"展开：
1. 架构：Erlang 负责连接和业务，C++ 负责战斗计算；三种接入方式的取舍（第 9、19 课）。
2. 设计亮点任选其一：Buff 系统的四个正交组件（数据驱动）、配置热更新的"锁外加载、锁内换指针"、确定性的保证措施。
3. 问题和解决过程：故事一或故事二，挑讲得最熟的那个。
4. 收尾用数据：吞吐、延迟、并发加速比。

讲的时候准备一张**架构图**（第 19 课第 4 节、第 20 课第 1 节都可以直接用），线上面试共享屏幕，线下面试在白板上画。

## 6. 被问到不会的问题怎么办

- **不要编**。C++ 面试官很容易识破，一旦被识破，前面所有的回答都会被打折扣。
- **说出你知道的部分，以及你会怎么去查证**。比如被问到 `std::atomic<std::shared_ptr>` 的具体实现："我测过 libstdc++ 里它不是 lock-free 的，内部应该是用了锁位，具体实现细节我没有读过源码。"
- **把问题引回你熟悉的领域**。被问到没做过的 io_uring："我用的是 epoll，了解 io_uring 的思路是批量提交、批量收取以减少系统调用。我在项目里用 strace 统计过系统调用，发现主要开销其实在锁和内存分配上，所以对我的场景来说，换 io_uring 的收益可能不如先优化分配。"

## 8. 课程总结

24 课走下来，你接触到的内容可以归成五层：

```
求职层     第 23~24 课  题库、简历、三个故事
工程层     第 11、21~22 课  构建、测试、性能分析、线上排查、模糊测试
系统层     第 17~20 课  线程、内存模型、epoll 服务器、游戏服务器架构
语言层     第 1~8、12~16 课  从项目代码出发，到对象模型、移动语义、智能指针、模板、STL 原理
对接层     第 9~10 课  Erlang Port / NIF、ETF 协议、配置管线
```

这些内容都围绕同一个项目展开，每一层都能落到具体的代码和实测数据上。面试时，这比"看过几本 C++ 书"有说服力得多。
